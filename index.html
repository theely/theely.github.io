Field notes · RL infrastructureScaling one training loop

8B to 700B

One reinforcement-learning loop, run four ways on Alps — and the memory wall, framework gap or reward bug that had to be solved each time.

EP
Elia Palme Sep 23, 2026 · 14 min read

Overview

Reinforcement learning on a language model is a loop with two different programs inside it. An inference engine generates answers to prompts as fast as it can. A reward function scores them. A training engine recomputes the probability of every generated token and turns those scores into gradients. Then the updated weights are pushed back into the inference engine, so the next batch of answers comes from the improved model. veRL is the framework that orchestrates that loop.

What follows is that loop run four ways on the Alps supercomputer: Apertus 8B on grade-school math, Apertus-v1.5 at 70B on the same data, the same 70B model on competition-level math, and GLM-5.1 and DeepSeek-V3 in the 700B mixture-of-experts class. Each combination of model and dataset gets a section below, in order of the fleet it needed — 4 GPUs, then 64, then 160, then 512 — and every one of them needed something built or fixed before a single clean training step would run.

The arithmetic of that progression is the part worth front-loading, because it is not linear. Going from 8B to 700B is about 87× the parameters, but it took 128× the GPUs — and per-GPU occupancy never fell much below two thirds of a 96 GB GPU at any point along the way. Three things bend the curve. Weights are the smallest part of what has to be stored: at 700B they are roughly 1.4 TB of an 11 TB training state, with gradients and optimizer state making up the rest. A fixed slice of every GPU goes to communication buffers and CUDA context, and that slice grows with the size of the communicator instead of shrinking with sharding. And the dataset counts as much as the model — a task whose answers run to 12,000 tokens instead of 2,000 changes the memory profile without changing a single parameter.

combination 1

Apertus 8B · GSM8K

Running an RL climb on an open-source, well-integrated 8B model such as Apertus is relatively straightforward. The figure below sets out the memory requirements for such a climb; every later section repeats it on the same grid, so it doubles as the reference for how memory pressure grows as the setups get more demanding.

Training an eight-billion-parameter model in bf16 with an Adam optimizer takes about 128 GB of state; sharded four ways by FSDP that is 32 GB per GPU. At that size the inference engine and the trainer can sit on the same GPUs, which makes the weight sync after each update a local copy rather than a network transfer.

The headroom is thinner than it looks. The inference engine also reserves a large share of each GPU up front, for its own copy of the weights and for the key-value cache, and the trainer needs 38 GB of what remains — so the two together occupy 86 of 96 GB. That makes gpu_memory_utilization the parameter to get right, because it does two jobs at once: it is the value that makes colocation fit, and it is also the value that decides how much cache the inference engine has to work with — on SGLang it maps to mem_fraction_static, the fraction of free GPU memory handed to static allocations like model weights and KV cache. Set it too high and SGLang claims memory the trainer needs; set it too low and generation throttles for want of cache.

Two properties of this configuration are what make that weight transfer cheap, and they are worth separating because they stop being true at different points later on. Colocation means the trainer and the inference engine occupy the same GPUs — in veRL’s hybrid-engine mode, the same process — rather than two separate pools. Synchronous training means each step generates with the current weights, trains on exactly that data, and only then updates, so one policy version is in flight at a time. Colocation is what makes the handoff local: the updated tensors already sit in the address space the inference engine reads from, so the update is a device-side copy rather than a serialise-and-ship across the network. Synchrony is what makes it simple: what the trainer just wrote is what the next batch of generations uses, so there is no version to track and no staleness to correct for — which is no longer the case with an async setup. The price is that the two phases cannot overlap. The device itself is never idle — one engine or the other is always computing on it — but whichever engine is running, the other one’s share of the memory sits reserved and unused, so roughly half of each GPU is capital you are paying for and not using.

combination 2

Apertus-v1.5 70B · GSM8K

Moving up in scale meant Apertus-v1.5-70B, and that is a bigger change than going from 8B to 70B parameters. The step to v1.5 also meant a newly released architecture, one that most frameworks in the loop did not yet support. Two things had to change as a result, and neither is a tuning problem: the architecture needed explicit support added to each of those frameworks, and the training loop itself needed a different placement.

Takeaway 1A model is not a portable artifact — every engine in the loop implements it separately

Three implementations of one model

An RL training loop holds the same model in three places, and they are three independent codebases.

  • transformers — the reference: it defines the config schema, the canonical parameter names, the tokenizer and the chat template, and everything else is specified relative to it.
  • SGLang — the inference engine, a second implementation written for decoding rather than differentiation: paged key-value cache, fused kernels, CUDA-graph capture, its own tensor-parallel split.
  • Megatron — the training engine, a third implementation: a GPTModel with fused QKV projections, its own layer specification, and its own parallelism, reached through Megatron Bridge, which maps every reference tensor onto a Megatron parameter and back.

FSDP is the exception — it wraps the reference module directly — which is why FSDP is usually the fast path for a new architecture and Megatron is not.

What Megatron Bridge does

Megatron Bridge does two jobs: a provider translates the reference config into Megatron’s own model config — layer count, hidden size, attention heads, normalisation, activation, rope parameters, vocabulary size — and a mapping registry relates every parameter in the checkpoint to its counterpart in the parallel model along with the transform between them, so the checkpoint’s separate query, key and value projections become Megatron’s fused linear_qkv, each mapping declares how its tensor splits across tensor-parallel ranks, and tied embeddings are declared as tied.

None of that is generic code; it is written per architecture, which makes it a fourth thing to patch. Any trainer that keeps its own parallel parameter layout requires the same mapping; this is not the case with FSDP. For Apertus-v1.5 it had to be written from scratch.

The following checklist should help as guidance when implementing support for a new model. Confirm that:

  • the reference implementation (e.g. transformers) recognises it;
  • the inference engine (e.g. SGLang) has a real model class rather than a generic fallback;
  • the training bridge, where one is needed (e.g. Megatron Bridge), exists in both directions;
  • every non-standard op has a kernel on both sides;
  • any asymmetry between input and output embeddings is representable in the trainer's parameter model.

Takeaway 2Placement sets the memory ceiling and decides how weights move

With a larger model the colocated arrangement becomes harder to sustain, because memory pressure rises against a fixed per-GPU budget. Generation also takes longer, and moving from synchronous to asynchronous training is what buys that time back.

Colocated (veRL calls it the hybrid engine) puts both engines on the same GPUs and alternates between them. Its advantage is the weight update: the trainer already owns the tensors the inference engine needs, on the same device, so the update is a local copy and the two copies are the same version by construction. The main challenge with this placement is memory pressure. An inference engine reserves a static fraction of each GPU for weights and key-value cache — 0.75 × 96 GB ≈ 71 GB here — so unless that reservation is released before the training phase, the peak on each GPU is the sum of both engines. Releasing it is not free either: it discards the key-value cache and pays a rebuild on the next generation phase.

That is precisely what failed at 70B. veRL's trainer starts a hybrid inference engine on every training GPU, so each GPU was asked to hold a 70B trainer shard alongside a 71 GB inference reservation. That shard needs 80 of the 96 GB on its own — 18 GB of weights, 35 GB of gradients, 19 GB of activations and about 8 GB of runtime, with the optimizer state already displaced to host RAM (Fig. 7). At 8B both fit; at 70B neither the sum nor the sleep-and-rebuild cycle was viable, and the setup moved to a disaggregated placement (hybrid_engine=False):

  • Trainer pool — 48 GPUs at eight-way tensor parallelism.
  • Rollout pool — 16 GPUs, four independent inference replicas at four-way.
  • Sharding — the trainer moved from FSDP to Megatron with it. FSDP splits along the data-parallel axis only, so each rank transiently holds whole layers, and in this implementation rank 0 materialised the entire model before sharding it: 92.5 of 95 GB on one GPU. Megatron’s tensor parallelism splits the weight matrices themselves, so no rank ever holds a whole layer — at eight-way it fits, while at four-way the gradient buffer alone requested 32.9 GB against 28.6 GB free.

What a weight update actually does

Once the pools are separate, a sync is not a copy — it is a re-shard. The trainer holds each parameter split along its own axes and in its own fusion conventions; the inference engine holds the same parameter split along different axes, often with QKV fused differently or not at all. So every sync must gather each parameter across the trainer's sharding axes into its whole-tensor form, convert it to the reference layout and naming, split it along the inference engine's layout, and load it into the serving process. Each of those gathers is a collective operation, and there is at least one per tensor: tens of thousands of collectives per sync. The cost and the fragility of weight sync are dominated by resharding collectives, not by raw bandwidth.

Splitting the pools asks for four things that colocation never needed:

  • A process group across both pools — established at startup and kept alive for the whole run.
  • A version number on the weights, because a replica can be halfway through generating when an update arrives.
  • An exact mapping between the two shardings. Getting it wrong is not loud: the model still runs and still generates, it is simply no longer the model the trainer thinks it is.
  • A second failure domain, because a dead rollout replica has to be noticed and replaced by the trainer.

Colocation has none of them: same device, same process, same version, one failure domain.

Unfortunately the change of topology was not smooth, and veRL v0.9.0 had to be patched. One patch stops the trainer starting an inference engine on every training GPU, each reserving its own share of the device, and drops a stale weight-sync call that crashed every rollout rank the first time a mid-run validation ran (local, two hunks). On v0.9.0 the flag above was not read at all, which is why that had to be a patch; veRL has since made it the documented switch for this trainer. The second patch keeps the standalone rollout on load_format: dummy, so it takes its weights from the first sync instead of reading the checkpoint off shared storage (verl #7422, merged upstream after v0.9.0).

Synchronous and asynchronous, and the price of throughput

The other question is whether generation and training run in sequence or in parallel. Run in sequence, each side waits for the other: the rollout pool idles while the trainer takes its step, and the trainer idles while the next batch is generated. Run in parallel, neither waits — and the samples the trainer consumes are no longer the ones its current weights produced.

Synchronous training consumes only data generated by the immediately preceding weights. This pipeline is called on-policy. The cost is utilisation: a step's duration is set by the longest sample in its batch, and the rest of the rollout pool idles while the trainer runs. On GSM8K, where answers are short and similar in length, that tail is small; on long-form reasoning it is not.

Asynchronous training lets generation run continuously and has the trainer consume batches as they complete, pushing weights every k updates. Utilisation goes up, and the data becomes stale: a batch produced under version v−1 or v−2 is used for a gradient applied to version v. The objective is then genuinely off-policy, and it has to be corrected. Async throughput is bought with staleness, and staleness is paid for in the objective. It also changes how to read one diagnostic. Both engines score the same sample: the inference engine records the probability it gave each token as it generated, and the trainer recomputes those probabilities from its own weights. Under colocated synchronous training the two are scoring the same tokens with the same weights, so they should differ only by small numerical noise — anything larger means something is broken, which makes it a useful alarm. Under async the two numbers come from different weight versions, so a gap is normal; what matters is that it stays small.

How the weights are transferred

Once the two pools are separate the weights have to travel, and three choices decide how much that costs:

  • How it travels — through a shared filesystem, through host memory, or straight from GPU to GPU over the interconnect.
  • How much is sent — every parameter, or only the values that changed since the last sync.
  • Who sends it — one rank gathers whole tensors and ships them, or every rank ships only the piece it already holds.

Only two of those shapes are things you can select. rollout.checkpoint_engine.backend takes nccl, which streams every parameter — with nixl, hccl and mooncake as alternative transports for the same shape, and naive for the colocated case, where there is no network to cross — or delta_sharded, which is the third and fourth rows at once; the name is both halves. Going via storage and quantising for transport are points in the design space rather than flags.

Cadence is a separate knob: syncing every update keeps the policy as fresh as possible and pays the transfer every step, while syncing every k updates amortises it and adds k steps of staleness on top of whatever the async pipeline already carries. This configuration used full NCCL sync every step — 144 GB in 8–10 seconds across 64 GPUs, roughly a sixth of a step. That is affordable at 70B and is exactly the design point that stops working at 700B, where the same strategy costs ~150 seconds and began to hang.

One further finding

Five runs on this configuration completed their steps with critic/score/mean at exactly 0.0 and grad_norm to match. GRPO derives its advantages from the spread of rewards within a group of samples for the same prompt, so a reward that is constant across the group — including constantly zero — yields zero advantage and therefore zero gradient, whatever the model is doing. The cause was the reward function, carried over unchanged from the 8B recipe: it credited only answers wrapped in <answer> tags, while Apertus-v1.5 terminates its solutions with Final answer: or a \boxed{} expression. The model was solving GSM8K correctly and being scored zero for it, and four of the five runs were spent looking for a weight-conversion fault that did not exist. The diagnostic that settled it was printing a sampled response next to its parsed answer. Reward parsing is part of the model interface, not a detail of the dataset — and a flat reward curve is evidence about the reward function at least as much as about the policy.

combination 3

Apertus-v1.5 70B · DAPO-Math

GSM8K stopped being a useful test of the infrastructure for two reasons. The models had learned to solve it near-perfectly within a handful of steps, and a model that is already right most of the time does not produce the long, varied, occasionally pathological responses that stress a rollout pipeline. It is also simple arithmetic: a correct GSM8K answer runs to about 300 tokens. Competition-level problems need a long reasoning trace before the answer can be stated, which puts mean response length in the thousands — and the memory a run needs follows response length. DAPO-Math, with AIME-2024 held out for evaluation, supplies both. The model is unchanged; the sequence budget is not. Prompts grow from 512 to 2,048 tokens and the response cap from 2,048 to 12,288, so one sequence goes from 2,560 tokens to 14,336. Two limits moved, and the 5.6× between them is what drives most of what follows.

Sequence length enters the memory budget in two places, and they behave differently. On the trainer it enters through activations, but activations are bounded by a per-GPU token budget rather than by the response cap: dynamic batching packs at most ppo_max_token_len_per_gpu tokens into a micro-batch, so a longer response yields more micro-batches per step rather than a taller activation peak. The budget here in fact went slightly down, 16,384 to 14,336 tokens per GPU, which is why the trainer bar in Fig. 11 is near-identical to Fig. 7. On the rollout it enters through the key-value cache, which is allocated per token held in flight and cannot be capped the same way, because the engine has to keep the whole sequence resident until generation finishes. At 5.6× the tokens per sequence, a replica with a fixed KV pool holds roughly 5.6× fewer sequences concurrently, so generation throughput per GPU falls by about the same factor. The only way to keep the trainer fed is more replicas: the rollout pool went from 16 GPUs in four replicas to 64 in sixteen, and the job from 16 nodes to 40. Response length is bought with generation hardware, not with trainer memory.

Longer responses drive up per-GPU memory use, so the setup had to be adjusted in five places:

  • use_fused_kernels: True — a fused cross-entropy kernel. The last layer scores every token in the micro-batch against every entry in the vocabulary, and for this model the vocabulary is 131,072 entries wide: at a 16,384-token micro-batch that one tensor is about 8.6 GB in fp32, the largest single allocation in the step, and the backward pass needs another of the same size. The fused kernel computes the loss and its gradient in chunks straight from the hidden states, so the tensor is never built at all.
  • ppo_max_token_len_per_gpu down to 14,336 — exactly one 2,048-token prompt plus one 12,288-token response, so dynamic batching cannot pack two full-length samples into a single micro-batch.
  • gpu_memory_utilization 0.75 → 0.65 — a smaller key-value-cache reservation on every rollout GPU. The knob sets what fraction of the device the inference engine claims up front for weights and KV cache.
  • update_weights_bucket_megabytes 2,048 → 512 — smaller weight-sync buckets, a quarter of veRL’s default. The receive buffers live on the rollout GPUs next to the inference engine, so they were competing for the same device memory as the line above.
  • grad-sync-empty-cache.patch — a cache flush before the gradient reduction, returning PyTorch’s cached-but-free blocks to the driver so NCCL can still allocate its collective buffers at the step boundary. A local patch around the hook veRL installs in register_megatron_training_hooks, not an upstream fix.

Lastly, one failure was not a matter of configuration at all but a real bug, and it was in a code path this run was the first to exercise. Until here the objective had taken the cheap route — veRL’s algorithm.rollout_correction.bypass_mode: True, which copies the probabilities the loss needs for the old policy straight from what the inference engine recorded as it generated. That is free, and it is only right if the generator and the trainer are the same model, which is exactly the assumption a disaggregated asynchronous setup gives up. Turning the flag off puts veRL in what it calls decoupled mode — three policies instead of two — and makes the trainer do the arithmetic itself:

  • it snapshots the policy the batch was generated under to host memory and re-scores the batch with its own weights, instead of trusting the generator’s numbers;
  • it weights each token by the ratio between the two, so the gradient accounts for the disagreement rather than ignoring it.

The cost of disabling bypass mode is one extra forward pass and a host-side copy of the weights every step; that copy raised the memory pressure further, and a bug in how veRL made it broke the run. Every step it asked the host for a new 18 GB buffer instead of reusing the one it already had, and the old ones were never handed back. Resident memory per rank climbed 40 → 82 → 104 GB, and a node exhausted its 450 GB by step three. Reusing one buffer holds it flat at 49–52 GB for a whole run, and went upstream as verl #7881.

Once the budget was adjusted for the longer responses and veRL was patched, the run itself worked: 92 of 92 steps, no crash, no hang, a checkpoint at the end. The training did not. AIME accuracy fell by more than half across the four evaluation checkpoints while the training reward climbed and mean response length collapsed from roughly 5,700 tokens to 510. The reward carried a length penalty written for this run rather than DAPO’s own overlong shaping — a soft penalty inside a buffer window, which its authors designed precisely because a naive length term gets gamed. The model duly found the cheapest way to satisfy ours: answer short, answer confidently, stop reasoning. It was getting better at the objective it had been given and worse at the task that objective was meant to stand for.

The intuition was that the length penalty in the reward function was collapsing response length and compromising the model’s reasoning. So the reward shaping was put to an A/B test. A second reward function — binary: one point for a correct final answer, nothing else, no format bonus and no length term — ran against the shaped one with everything else held fixed: same config, same correction, same 92 steps, same data.

combination 4

GLM-5.1 & DeepSeek-V3, 700B · GSM8K

The last step up is another factor of ten in parameters: GLM-5.1 and DeepSeek-V3, both 700B-class mixture-of-experts models, on 128 nodes — 512 GPUs, 480 of them training. One copy of the model in bf16 is 1.4 TB, and the state the job has to hold comes to 39 TB.

At this model size the optimizer state no longer fits on the GPU even sharded across data-parallel ranks. Three changes got the step through (as set in the recipe):

  • override_optimizer_config.optimizer_cpu_offload: True — the optimizer state lives in host memory and is streamed back a bucket at a time during the step, so the GPU never holds all of it. Three companion keys in the same block come with it: an offload fraction, D2H/H2D overlap, and the precision-aware optimizer that path requires.
  • override_optimizer_config.main_grads_dtype: bf16 — halves the gradient buffer, which holds a gradient for every local parameter during the backward pass and does not shard.
  • model.use_fused_kernels: True — the same fused cross-entropy kernel as the 70B run, for the same reason.

Host RAM promptly became the new wall at 446 of 450 GB per node, which is what megatron.param_offload: False answers: with the optimizer already on the host, the weights have to stay resident on the GPU.

The move to a larger model also meant a fundamentally different architecture, and mixture-of-experts brought failure modes that have nothing to do with memory. In every layer a router picks which handful of experts a token visits. The rollout engine and the trainer compute that decision independently, and at this size their numbers do not always agree closely enough to pick the same experts. When they disagree, the trainer is not grading a slightly different probability for the token it sampled — it is grading a different sub-network, off-policy in a way the algorithm does not account for. The fix, Rollout Router Replay (R3), records which experts the rollout actually used and forces the trainer to replay them; it needs two flags set together, actor.megatron.router_replay.mode: R3 on the trainer and rollout.enable_rollout_routing_replay: True on the rollout.

Weight sync was the other new problem: at 700B a full sync is impractical. A delta-sharded sync sends only the parameters that changed, which cuts what has to cross the network; switching to it is one line, rollout.checkpoint_engine.backend: delta_sharded, and veRL wires up the matching engine and the inference-engine loader it needs. That exposed two bugs of its own, since the new path gathered every changed value across the full training world into padded buffers on a single rank, and a third in the inference engine's weight loader. All three went upstream — a point-to-point gather and a per-round memory cap (verl #7777, #7778), and a caching fix in SGLang's fused QKV loader that had been silently leaving half of an attention projection randomly initialised whenever an update arrived split across two calls (sglang #38298). A fourth, further upstream in how training batches were reassembled, was collapsing same-length responses into the wrong tensor layout (verl #7661).
